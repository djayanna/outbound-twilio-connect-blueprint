Twilio Connect Blueprint — Overview

Twilio Connect Blueprint

A reference implementation showing how a customer-facing application wires the Twilio stack — Agent Connect, ConversationRelay, Conversation Orchestrator, Memory, Intelligence, and Event Streams — to run outbound voice + SMS conversations driven by an LLM agent. Upstream apps post Jobs that describe who to reach and why; the scheduler enforces how and when — quiet hours, consent, retries, channel fallback — and reports progress back via upstream_callback_url.

01

Why you'd build this

Most businesses have systems of record that know when a customer needs to be contacted — the EHR knows tomorrow's appointments, the OMS knows which package is 20 minutes out, the growth database knows which users haven't opened the app in three weeks. Those systems weren't designed to run the actual conversation. A cron inside the CRM firing SMS is enough until the first time it texts someone at 2 a.m., skips a time zone, double-dials on a retry, or has no record of whether the customer actually heard back.

Healthcare appointment confirmations and reminders
The EHR files the appointment; this layer calls or texts the patient the day before, confirms or reschedules in natural language, and writes the outcome back. Consent is implied by the care relationship, but TCPA quiet hours and HIPAA posture still apply.
Last-mile delivery communications
The OMS hands off a shipment; this layer sends an ETA SMS, handles "I'm not home" replies, offers to reschedule, and escalates to voice if a signature is required. Timezone of the recipient, not the warehouse, drives timing.
Re-engaging quiet users
Growth tooling flags customers who've gone silent — abandoned carts, lapsed subscriptions, trial users who never activated. This layer runs a short, personalized conversation (voice for high-value accounts, SMS otherwise), captures the reason for the drop-off into Memory, and feeds the result back to the upstream system.

The common shape: an upstream system knows that a conversation should happen, but running it well requires policy (TCPA, consent, DNC), reliability (retries, channel fallback, dedupe), and conversational intelligence (identity resolution, memory of prior interactions, operator-driven follow-ups). This blueprint is where those three concerns live.

02

Mental model: a policy-aware broker for conversations

If you've worked with a message queue, the shape will be familiar.

Message queueThis blueprint
Producer publishes a message Upstream app POST /jobs
Broker holds and routes work Scheduler holds Jobs, applies policy, picks the moment to fire
Delivery rules (retry, DLQ, ordering) Quiet hours, consent, retries, channel fallback, dedupe, concurrency
Consumer processes the message agent-connect runs the LLM conversation over Twilio
Ack / nack back to producer upstream_callback_url POSTs on each Job lifecycle event
Dead-letter queue JobRun.status = failed with terminal_reason, surfaced in audit + wallboard

The analogy is a mental model, not an infrastructure claim — the scheduler is in-process sqlite, not Kafka. The twist versus a generic queue is that the delivery policy is domain-aware (TCPA, timezone-local quiet hours, consent records) and the "work" being delivered is a stateful, LLM-driven conversation rather than a one-shot message.

03

What this blueprint shows

How to post work to a scheduler
Any upstream system (CRM, billing, portal) creates a Job; the scheduler decides when, how, and whether to execute it.
How the scheduler enforces business policy
Time windows (TCPA quiet hours in recipient's TZ), consent, do-not-contact suppression, retries, channel fallback, dedupe, concurrency caps.
How Twilio Agent Connect bridges an LLM to Twilio channels
TAC handles inbound webhooks and outbound conversations across voice (ConversationRelay) and SMS, with Memory wired in for identity resolution and persistent context.
How Event Streams feeds state back
Account-level events — Intelligence operator results, errors, resource lifecycle — land in a single ingestor that validates, dedupes, and appends. Scheduler and wallboard read from the store on their own cadence.
How to observe the system end-to-end
OpenTelemetry traces across every service, an append-only audit log for business events, and a live wallboard for operators.

Service · scheduler

scheduler

:3001 · FastAPI · Python 3.11

The brain. Owns Jobs, JobRuns, and audit.db. All business policy lives here — upstream apps don't make scheduling decisions, this service does.

Responsibilities
  • Accept POST /jobs from upstream apps and the test-harness.
  • Run policy before firing: TCPA quiet hours in the recipient's timezone, consent gate (no marketing SMS without a record), do-not-contact suppression, dedupe on (scenario, to), concurrency caps per campaign.
  • Fire outbound by calling agent-connect's /outbound, with statusCallback on Calls.create / Messages.create pointing at scheduler's own endpoint.
  • Advance JobRun state on per-call / per-message StatusCallback, with no event-ingestor hop.
  • Retry + channel fallback (voice no-answer → SMS).
  • Report back to upstream via upstream_callback_url on each lifecycle transition.

Service · agent-connect

agent-connect

:3002 · FastAPI · TAC · Python 3.11

The Twilio Agent Connect application. The LLM-powered conversation runtime that connects your LLM to Twilio's channels — inbound and outbound, voice and SMS.

Responsibilities
  • Inbound SMS webhook via TAC's SMSChannel, configured on the Twilio number.
  • Inbound + outbound voice via ConversationRelay (TAC's VoiceChannel) — WebSocket for the STT/TTS + LLM turn loop.
  • Memory retrieval before each response — identity resolution + Recall against Conversation Memory.
  • Orchestrator session management — Conversation + Communication state on the Twilio side.
  • Tools exposed via @function_tool (lookup account, schedule callback, transfer, etc.) called by the LLM mid-conversation.
  • Outbound conversation creation on behalf of the scheduler.

Service · event-ingestor

event-ingestor

:3003 · FastAPI · Python 3.11

A dumb sink for account-level Twilio Event Streams and scheduler-emitted lifecycle events. It validates, dedupes, and appends. No routing, no business logic.

Responsibilities
  • POST /twilio/events — Twilio Event Streams webhook sink.
  • Validate Twilio signature on every request using RequestValidator.
  • Dedupe on event id via the seen_events sqlite table — Event Streams is at-least-once.
  • Append every event to the event store (Intelligence OperatorResult, errors, account-wide events).
  • Accept scheduler-emitted events so the wallboard has a single store to read from.
What it does NOT do
  • Does not route events to scheduler. Per-call / per-message lifecycle goes directly to scheduler via Twilio StatusCallback.
  • Does not classify event types. Consumers (wallboard, debuggers) decide which events are relevant when they read.

05

Architecture

Services · Twilio products · caller

Three inbound surfaces from Twilio, each configured where the resource lives: per-call StatusCallback → scheduler, phone-number inbound webhooks → agent-connect, account-level Event Streams → event-ingestor.

  1. Upstream (or test-harness during dev) posts a Job to scheduler, optionally including an upstream_callback_url. scheduler POSTs lifecycle events (accepted / suppressed / per-JobRun transitions / terminal outcome) back to that URL as the Job progresses.
  2. scheduler runs policy (quiet hours, consent, DNC, dedupe, concurrency), then calls agent-connect to fire outbound. The statusCallback URL on Calls.create / Messages.create points at scheduler's own endpoint.
  3. agent-connect opens a ConversationRelay session (voice) or sends via Messages (SMS), hydrating with Conversation Memory and driven by the LLM.
  4. Conversation Intelligence runs operators (summary, sentiment) over the transcript as it accumulates.
  5. Event Streams emits account-level events to event-ingestor, which validates, dedupes, and appends. scheduler also dumps its own JobRun lifecycle events into event-ingestor so there is a single event store.
  6. Per-call lifecycle events (ringing, answered, completed, AMD) flow back to scheduler directly via StatusCallback, advancing the JobRun.
  7. wallboard reads from event-ingestor on a 2s poll for the live operator view.
06

Core concepts

Job vs JobRun

Job is the business intent — "contact this customer at this time for this reason." Immutable once accepted.

JobRun is one execution attempt. Retries create new JobRuns against the same Job. conversation_id lives on JobRun, not Job — the Conversation is Twilio-side state created when the Job fires.

Three inbound surfaces

StatusCallback — per-call lifecycle for calls scheduler originated. Points at scheduler.

Phone-number webhooks — end-user-initiated calls and SMS. Point at agent-connect.

Event Streams — account-wide events, Intelligence operator results, errors. Point at event-ingestor.

Vocabulary

The blueprint uses its own terms (Job, JobRun, Scenario) and never reuses Twilio's Conversation or Communication as business-side identifiers — those stay as Twilio-side ids inside JobRun.

Tracing vs auditing

Tracing (OpenTelemetry) answers "where did time go, where did it fail?" — short retention, high volume.

Auditing (append-only audit.db owned by scheduler) answers "who did what, when?" — long retention, explicit audit.record(...) calls.

The scheduler owns the lifecycle: it posts outbound, receives the per-call StatusCallback, and advances the JobRun. agent-connect owns the conversation runtime via ConversationRelay.
